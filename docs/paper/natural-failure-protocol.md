# Natural-failure study protocol (§5.6)

**Status:** Protocol only. No results in this document. Numbers are
produced in Week 8 by human annotation, not by this protocol and not by
the harness.

This document specifies the protocol for the natural-failure study that
backs **CLAIMS.md claim 4** ("Natural-failure agreement"). It exists so
the study is pre-registered: the held-out selection, generation,
question set, rubric, agreement target, and the one table it produces
are all fixed *before* any candidate output is graded.

## Why this study exists (the open defense)

This is the explicit defense against the second predicted reviewer
attack in CLAIMS.md: **"Your injected failures are too easy."** The
matched-pair injected benchmark (254 seeds → 1,270 examples) shows the
three rules are operationally non-overlapping under *controlled*
failures. It does not show that real LLMs, generating freely, produce
failures the validator catches. If injected failures were artificially
crisp (e.g. a fabricated span ID is trivially outside the key space, an
out-of-context span is trivially absent from the prompt set), the
decomposition could be an artifact of construction.

The natural-failure study removes injection entirely: real models
answer real held-out questions, humans grade what actually came out, and
we report — without spin — how the validator's typed refusals line up
with the human grade. The honest result is reported whether or not it
flatters the system. A low natural-failure agreement is a publishable
limitation, not a study to bury.

## Grading is human. The harness does NOT auto-grade.

The harness's role in this study is **strictly preparatory**. The
`evidence-eval natfail-prep` subcommand runs candidate outputs through
the validator and emits an annotation **worksheet** with the validator's
typed refusal recorded in one column and a deliberately **blank human
label column**. It produces no agreement number, no precision, no
recall. The final table is computed from the human labels after
double-annotation and adjudication.

This separation is load-bearing. If the harness graded itself against
the validator, the study would be circular — it would measure the
validator against the validator. The validator's verdict is the
*system under test*; the human label is the *ground truth*. They must be
produced independently.

## 1. Held-out label selection

The natural-failure corpus is drawn from FDA drug labels **held out from
the 50-label benchmark corpus**, so no model or author has tuned against
them.

- **Source.** The DailyMed fetch (`evidence-eval fetch dailymed`) is
  re-run with a larger `--limit` to obtain a label pool strictly
  disjoint from the 50 labels used to author the 254 benchmark seeds.
  Disjointness is enforced by SPL set-id: any label whose set-id appears
  in `fda_label_bench_PROVENANCE.md` is excluded.
- **Count.** Select **15 held-out labels**, stratified to mirror the
  benchmark's section mix (contraindications, dosing, warnings, drug
  interactions, adverse reactions) so the question set is not skewed
  toward one section type.
- **Freeze.** The 15 set-ids are recorded in this directory before
  generation begins and are not changed once a single answer is
  generated. Adding or swapping a label after generation invalidates the
  pre-registration.

## 2. Question set

From the 15 held-out labels we author **20 questions** spanning the same
five question types the benchmark uses (single-span factual, multi-span,
negation, quantitative, contraindication). Questions are written by the
author from the label text *only* — they are retrieval/answering
prompts, not graded items, so authoring them does not contaminate the
study. Each question has a documented gold answer and gold span set used
later only as an annotation aid, never as an automatic grader.

Question-type quota (20 total):

| Type | Count |
|---|---|
| Single-span factual | 6 |
| Multi-span | 4 |
| Negation | 3 |
| Quantitative | 4 |
| Contraindication | 3 |

## 3. Candidate generation models

Answers are generated by the same backends named in CLAIMS.md so the
study is consistent with the rest of the paper:

- **Llama 3.1 8B** (Ollama, open).
- **Qwen 2.5 7B** (Ollama, open).
- **One closed reference** (Claude Haiku or GPT-4o-mini — whichever is
  fixed at study start and recorded here).

Each model answers all 20 questions under the same RAG harness used
elsewhere (retrieve chunks from the held-out label, prompt the model to
answer with span citations). Decoding settings (temperature, top-p) are
recorded with the run. No injection, no contrast-set rewriting: whatever
the model emits is what gets graded.

## 4. Sample size

3 models × 20 questions = **60 question-model pairs**. Each answer is
multi-sentence; the unit of annotation is the **(sentence, citation)
claim**, of which there are typically 3–6 per answer. This yields an
expected **~180–360 graded claims**, sitting in the
**~150–300 generated-output** band the study targets. If a model
declines or returns a degenerate answer for some questions, the floor
(~150) is protected by sampling up to 5 additional held-out questions
from the existing 15 labels until ≥150 gradable claims exist. Sampling
expansion (if any) is logged.

Rationale: the study's headline is a per-class agreement table, not a
single proportion, so the relevant power is per-class cell counts. ~150
claims is the minimum at which the smallest expected class
(contradicted) is likely to have ≥10 instances; ~300 gives every class
a double-digit cell. Beyond ~300 the marginal annotation cost is not
justified for a §5.6 supplementary study.

## 5. Annotation rubric

Two annotators independently label **every (sentence, citation) claim**
into exactly one of the following. The first six are the validator's
own classes (`evidence-eval`'s `HallucinationClass`); the last two are
annotation-only and never produced by the validator.

| Label | Definition (annotator sees: sentence, cited span text, prompt chunk set, full label) |
|---|---|
| `valid` | The cited span exists, was in the prompt, and entails the sentence. |
| `uncited` | The sentence makes a factual claim but carries no citation. |
| `fabricated_span` | The citation points to a span ID that does not exist in the label's corpus. |
| `out_of_context` | The cited span exists in the label but was not in the prompt chunk set the model saw. |
| `unsupported` | The cited span exists and was in context but does not entail the sentence (neutral / off-topic). |
| `contradicted` | The cited span exists and was in context but contradicts the sentence. |
| `partial_support` | The span entails *part* of a multi-clause sentence but not all of it. Annotation-only; rolled into `unsupported` for the headline table and reported separately as a secondary cut. |
| `ambiguous` | The annotator cannot confidently assign one class (e.g. the sentence is non-factual hedging, or the gold answer itself is unclear). Excluded from the agreement table; counted and reported as a coverage caveat. |

Annotators work from a shared written guideline with two worked
examples per class. They do **not** see the validator's verdict column
while labeling (the worksheet's validator column is withheld in the
annotation copy; see §7).

## 6. Inter-annotator agreement

- Both annotators label all gradable claims independently.
- Agreement is measured with **Cohen's κ** over the six validator
  classes (`partial_support` folded into `unsupported`, `ambiguous`
  excluded).
- **Target: κ ≥ 0.70** (substantial agreement). If κ < 0.70 the rubric
  is revised, both annotators re-trained on a fresh guideline, and the
  full set re-annotated — the study is not reported on a rubric that did
  not reach the bar.
- **Adjudication.** Claims where the two annotators disagree are
  resolved by a third adjudicator to a single gold label. The
  adjudicated gold label — not either individual annotation — is what
  the headline table is computed against. κ is reported on the
  *pre-adjudication* labels (it measures rubric reliability, not
  post-hoc consensus).

## 7. Worksheet and blinding

`evidence-eval natfail-prep <answers.toml>` consumes a TOML in the
standard `Example` schema (`corpus_spans` / `prompt_chunks` /
`response_sentences` with the model's `cited_spans`; `class` is a
to-be-human-labeled placeholder) and runs every item through the
validator via the existing policy stack (`run_with_model`, three-gate).
It emits a markdown worksheet with, per claim:

- the example name and the sentence text,
- the cited spans,
- **the validator's typed verdict**: one of `UnknownSpan`,
  `OutOfContext`, `Unsupported`, `Contradicted`, or `accept`,
- a **blank human-label column** for annotators to fill.

Two physical copies are derived from this worksheet:

1. **Annotation copy** — the validator-verdict column is blanked out.
   This is what the two annotators fill in, so the validator's opinion
   cannot anchor them.
2. **Scoring copy** — the full worksheet, retained by the study runner,
   used only after adjudication to join human gold labels against the
   validator verdict.

The harness emits the scoring copy. The annotation copy is the scoring
copy with one column cleared; that clearing is a manual,
documented step, not a harness feature, to keep the harness's surface
honest (it produces a worksheet, never a graded result).

## 8. The one table this study produces

The study produces exactly **one headline table**: per validator class,
the human count, how many the validator caught, and the resulting
precision / recall.

| Class | Human count | Validator-caught | Precision | Recall |
|---|---|---|---|---|
| `uncited` | … | … | … | … |
| `fabricated_span` | … | … | … | … |
| `out_of_context` | … | … | … | … |
| `unsupported` | … | … | … | … |
| `contradicted` | … | … | … | … |
| **overall (any failure)** | … | … | … | … |

Cells are filled **only** from adjudicated human gold labels joined to
the validator verdict. They are intentionally left as `…` in this
protocol. Definitions:

- **Human count** — claims the adjudicated gold label assigned to that
  class.
- **Validator-caught** — of those, how many the validator refused with
  the *matching* typed refusal (a class is "caught" only by its owning
  gate's refusal, not by any refusal — an `unsupported` claim refused as
  `OutOfContext` is a wrong-reason catch and is reported separately, not
  counted here).
- **Precision** — over all claims the validator refused with that typed
  refusal, the fraction whose gold label matches.
- **Recall** — over all claims with that gold label, the fraction the
  validator caught with the matching refusal.

A secondary table reports `partial_support` and wrong-reason catches;
an `ambiguous` count and the κ value are reported in the surrounding
prose as caveats.

## 9. Pre-registration checklist

Before the first answer is generated, the following are frozen and
recorded in this directory:

- [ ] 15 held-out label set-ids (disjoint from benchmark provenance).
- [ ] 20 questions with gold answers and gold spans.
- [ ] The three generation models and their decoding settings.
- [ ] The two annotators and the adjudicator (named, no overlap with
      benchmark seed authoring where avoidable; any overlap disclosed).
- [ ] κ target (0.70) and the re-annotation rule if it is missed.
- [ ] This table schema.

Any deviation from a frozen item after generation begins is logged in a
deviations section appended to this file and disclosed in the paper.
